# USW SYNC (임시 명칭)

수원대학교 학생들을 위한 **공강 기반 팀플 일정 자동 조율 및 협업 관리 PWA**를 개발할 예정입니다. 프로젝트명은 추후 변경될 수 있습니다.

현재는 구조와 문서를 정리하는 초기 단계입니다. 아래 기능과 시스템 구성은 모두 개발 계획이며, 신규 서비스 코드·API·데이터베이스·PWA·배포 환경은 아직 구현하거나 구성하지 않았습니다. 4명의 팀원이 담당 업무를 논의한 후 개발을 시작하며, 역할은 아직 정하지 않았습니다.

## 개발 배경 및 문제점

수업 팀플, 공모전, 해커톤 등에서 팀원마다 시간표가 달라 공통으로 가능한 시간을 찾기 어렵습니다. 회의 일정, 역할 분담, 할 일과 마감일도 여러 플랫폼에 분산되어 진행 상황을 확인하기 불편합니다.

## 프로젝트 목표

이미 구성된 팀이 개인 시간표와 활동 가능 시간을 등록하면 공통 공강을 자동으로 찾고, 회의 추천·투표·확정부터 업무와 마감일 관리까지 한곳에서 처리하도록 지원합니다.

**팀원 모집 게시판, 공개 모집글, 지원자 매칭은 개발 범위에 포함하지 않습니다.** 스포츠 인원 모집 프로젝트와 구분하여 기존 팀의 일정 조율과 협업 관리에 집중합니다.

## 주요 기능 (계획)

1. 회원가입 및 로그인
2. 팀 생성 및 초대 링크를 통한 팀원 참여
3. 개인 시간표 및 활동 가능 시간 등록
4. 팀원 간 공통 공강 시간 자동 탐색
5. 회의 가능 시간 추천 및 투표
6. 회의 일정 확정 및 관리
7. 팀원별 역할 분담 및 할 일 관리
8. 과제 마감일 및 진행 상황 관리

모든 기능은 개발 예정입니다. 시간표 입력 방식, 공강 계산 기준, 회의 추천·투표 정책과 접근 권한은 요구사항 논의 후 결정합니다.

## 기술 스택

| 영역 | 현재 계획 (미확정) |
| --- | --- |
| 프런트엔드 | React + TypeScript |
| UI | Tailwind CSS |
| 백엔드 | Python FastAPI |
| API | FastAPI 기반 자체 REST API |
| 데이터베이스 | PostgreSQL (Supabase 활용 예정) |
| 프런트엔드 배포 | Vercel |
| 백엔드 배포 | Render |
| 모바일 지원 | 반응형 웹 및 PWA |
| 버전 관리 | GitHub |

위 구성은 확정 사항이 아닙니다. 기술 변경이 쉽도록 화면, 서비스 로직, 데이터베이스 설계, 문서를 분리합니다. 세부 디렉터리와 라이브러리는 담당 업무와 기술 스택 확정 후 추가합니다.

무료 플랜을 활용해 개발과 경진대회 시연 시 별도 운영 비용이 발생하지 않는 구성을 목표로 합니다. 서비스별 무료 플랜의 제한과 이용 조건은 배포 전에 확인합니다.

## 전체 시스템 구조 (계획)

```text
학생의 모바일·PC 브라우저 / 설치형 PWA
                    ↕
React + TypeScript (Vercel 예정)
                    ↕ HTTPS · REST API
Python FastAPI (Render 예정)
                    ↕ 데이터베이스 연동
PostgreSQL (Supabase 예정)
```

화면은 입력과 결과 표시를, 백엔드는 인증·팀별 접근 권한 검증, 공강 계산, 일정·업무 관리와 DB 연동을 담당할 예정입니다. API 코드는 `backend/` 내부에서 관리하며, 별도 최상위 API 폴더는 만들지 않습니다. 인증 방식, 데이터 모델과 배포 세부 구성은 추후 설계합니다.

## 프로젝트 디렉터리 구조

```text
.
├── frontend/
│   └── README.md
├── backend/
│   └── README.md
├── database/
│   └── README.md
├── docs/
│   └── README.md
├── .github/
│   └── .gitkeep
├── .gitignore
├── AGENTS.md
├── CLAUDE.md
└── README.md
```

| 폴더 | 역할 |
| --- | --- |
| [`frontend/`](frontend/README.md) | React 화면, 모바일 반응형 UI 및 PWA |
| [`backend/`](backend/README.md) | FastAPI 서비스 로직과 자체 REST API |
| [`database/`](database/README.md) | 데이터 모델, 추후 SQL 스키마·마이그레이션·테스트 데이터 |
| [`docs/`](docs/README.md) | 요구사항, API 명세, DB 설계, 아키텍처, 일정 및 테스트 계획 |
| `.github/` | GitHub 협업 파일 관리 공간. 현재 템플릿·Actions는 없음 |

위 구조는 신규 프로젝트의 기본 구조입니다. Git은 빈 폴더를 추적하지 않으므로 `.github/.gitkeep`만 추가합니다. PR 템플릿이나 자동화 설정은 아직 추가하지 않습니다. 기존 AI 협업 지침은 유지합니다.

이전 공지 수집 프로젝트의 `crawler/`는 신규 서비스에서 사용하지 않으므로 사용자 승인 후 삭제했습니다. 기존 `tests/README.md`는 보존했으며, 공통 테스트 문서로 재사용할지 논의합니다. 추가 삭제·이동이 필요하면 대상 목록을 제시하고 승인 후 정리합니다.

## 개발 목표 및 2~4주 MVP 계획 (예정)

팀 생성부터 공통 공강 확인, 회의 확정, 업무·마감일 관리까지 이어지는 흐름을 시연하는 것이 목표입니다. 아래 일정은 4명이 역할을 협의하기 위한 초안이며 담당자나 완료 일정을 확정하지 않습니다.

| 기간 | 개발 예정 범위 | 확인할 결과 |
| --- | --- | --- |
| 1주 차 | 요구사항·MVP·기술 스택·역할 협의, 화면·API·DB 설계, 개발 환경 구성 | 입력 규칙, 권한 및 공강 계산 기준 합의 |
| 2주 차 | 인증, 팀 생성·초대 참여, 시간표·활동 가능 시간 등록, 공통 공강 탐색 | 팀의 공통 가능 시간을 확인하는 핵심 흐름 |
| 3주 차 | 회의 추천·투표·확정, 역할·할 일·마감일·진행 상황 관리 | 팀 일정과 업무의 연계 흐름 |
| 4주 차 | 모바일 반응형·PWA, 통합 테스트, 배포 조건 확인 후 시연 준비 | 모바일 사용성과 전체 시나리오 검증 |

2주 일정이라면 1~2주 차 핵심 흐름을 우선 MVP로 하고 3~4주 차 범위는 후속 개발로 조정할 예정입니다. 세부 우선순위는 팀 논의로 확정합니다. 이번 초기 정리에서는 기능 개발·환경 설치·배포를 수행하지 않습니다.

설치 및 실행 명령어는 개발 환경을 구성하고 검증한 후 추가합니다.

## GitHub 브랜치 구조

| 브랜치 | 역할 | 반영 원칙 |
| --- | --- | --- |
| `main` | 최종 검증된 안정적인 코드 | 프로젝트 관리자의 명시적 승인 후 별도 PR로만 병합 |
| `develop` | 팀원들의 기능 통합 | 개인 feature 브랜치의 PR을 검토한 후 병합 |
| `feature/이름` | 팀원별 개인 개발 | 본인의 브랜치에서 개발·Commit·Push |

- 일반적인 개발 작업에서 `main`을 수정하거나 직접 개발·Commit·Push하지 않습니다. AI 도구도 명시적 승인 없이 변경할 수 없습니다.
- `develop`에 직접 Commit하거나 Push하지 않습니다.
- 팀원마다 개인 feature 브랜치 하나를 만들고 지속적으로 재사용합니다. 기능마다 새 브랜치를 만들 필요는 없습니다.
- 브랜치 이름은 `feature/이름`으로 통일하며 영문 소문자를 권장합니다. 예: `feature/jinwoo`, `feature/minsu`, `feature/jihoon`.
- 다른 팀원의 feature 브랜치에서 직접 작업하거나 Push하지 않습니다. 새로운 팀원이 합류하면 해당 팀원의 브랜치를 추가합니다.
- 브랜치 이름은 담당자를 구분하는 데 사용하며, 실제 수정 이력은 Commit 작성자와 PR 기록으로 확인합니다.

## 팀원 협업 작업 순서

아래 명령은 팀원의 일반적인 협업 절차를 설명합니다. AI 도구에 Git 작업 실행을 자동으로 허가하는 지침은 아닙니다.

### 1. 최신 develop 확인

작업 중인 변경 사항을 안전하게 정리한 후 최신 코드를 가져옵니다.

```bash
git switch develop
git pull origin develop
```

### 2. 개인 feature 브랜치 준비

처음 작업하는 팀원은 최신 develop을 기준으로 브랜치를 생성합니다. `이름`은 자신의 영문 이름으로 바꿉니다.

```bash
git switch -c feature/이름
```

이미 브랜치가 있다면 기존 브랜치로 이동하여 최신 develop을 반영합니다.

```bash
git switch feature/이름
git merge develop
```

브랜치 전환이나 Merge 전에 작업 중인 변경 사항을 안전하게 정리합니다. 충돌이 발생하면 내용을 확인해 해결하며, 다른 팀원의 코드를 임의로 삭제하거나 덮어쓰지 않습니다.

### 3. 개인 feature 브랜치에서 개발

모든 코드 작성과 수정은 자신의 feature 브랜치에서 진행합니다. 여러 기능을 같은 브랜치에서 개발할 수 있습니다. 다른 팀원의 코드를 불필요하게 수정하지 않으며, 기존 기능에 영향을 주는 대규모 변경은 사전에 알립니다.

### 4. Commit 및 Push

변경 파일을 확인하고 비밀값과 불필요한 파일이 없는지 점검한 뒤 자신의 브랜치에 반영합니다.

```bash
git add .
git commit -m "작업 내용 설명"
git push origin feature/이름
```

Commit 메시지는 수정 내용을 명확하게 설명합니다. `main`과 `develop`에는 직접 Push하지 않습니다. AI 도구는 사용자의 명시적인 요청 없이 Commit이나 Push를 실행하지 않습니다.

### 5. Pull Request 생성 및 검토

- 일반 개발 PR은 자신의 feature 브랜치에서 `develop`을 대상으로 생성합니다.
- PR에는 주요 변경 내용과 테스트 실행 여부 및 결과를 작성합니다.
- 필요한 검토가 완료되면 `develop`에 Merge합니다. PR 없이 직접 Push하지 않습니다.
- `main` 병합은 일반 개발 PR과 별개로 프로젝트 관리자의 명시적 승인 후 별도 PR을 통해서만 진행합니다.

### 6. feature 브랜치 재사용

PR이 Merge된 후에도 개인 feature 브랜치를 삭제하지 않습니다. 다음 작업 전에 최신 develop을 가져와 같은 브랜치에 반영합니다. 이전 PR의 Commit이 다음 PR에 불필요하게 반복되지 않도록 이력을 확인합니다.

## 기존 코드 보호

- 기존 파일·기능을 임의로 삭제하거나 요청받지 않은 기능을 추가하지 않습니다.
- 다른 팀원의 코드를 불필요하게 변경하지 않습니다.
- 프로젝트 구조를 대규모로 변경하거나 기술 스택·핵심 라이브러리를 변경하려면 사전에 사용자에게 확인합니다.
- 다른 팀원의 작업에 영향을 줄 수 있는 변경은 사전에 알리고, 기존 기능에 대한 수정 이유와 영향을 설명합니다.
- Git 충돌에서 다른 팀원의 변경 사항을 임의로 덮어쓰지 않습니다.

## 보안 및 환경 관리

- API 키, 비밀번호, 인증 토큰 등 민감한 정보를 GitHub에 업로드하지 않습니다.
- 필요한 민감한 환경변수는 `.env`로 관리하고 `.gitignore`에 등록하여 Git 추적에서 제외합니다.
- 필요한 환경변수 목록은 실제 비밀값 없이 `.env.example`에 정리할 수 있습니다.
- 가상환경, 캐시, 임시 파일 등 불필요한 파일을 업로드하지 않습니다.
- 새로운 라이브러리를 설치하면 프로젝트에서 사용하는 의존성 관리 방식에 맞게 기록합니다.

## 코드 품질 및 테스트

새 기능은 가능한 범위에서 테스트하고 기존 기능도 정상 작동하는지 확인합니다. 중복 코드를 피하고 읽기 쉬운 코드를 작성하며, 임시 디버깅 코드와 불필요한 출력문을 정리합니다. 실행하지 않은 테스트를 성공했다고 보고하지 않습니다. 오류나 테스트 실패는 원인과 해결 여부를 명확하게 보고합니다.

## 변경 사항 보고

코드를 작성하거나 수정하면 다음 항목을 사용자에게 간결하게 보고합니다.

1. 생성하거나 수정한 파일
2. 변경한 기능과 주요 내용
3. 변경 이유
4. 기존 기능에 미칠 수 있는 영향
5. 테스트 실행 여부 및 결과
6. 추가 확인이 필요한 사항

문서 작업도 변경 파일과 내용을 보고합니다. 수정한 내용이 없으면 수정하지 않았다고 명시하고, 테스트를 실행하지 않았으면 진행하지 않았다고 명시합니다.

## AI 코딩 도구 공통 규칙

Codex, Claude Code 등 프로젝트에서 사용하는 모든 AI 코딩 도구에 적용합니다.

1. 작업 시작 전에 현재 Git 브랜치와 작업 중인 변경 사항을 확인합니다.
2. `main`을 임의로 수정하지 않습니다. `main`이면 수정 전에 사용자에게 알리고 명시적 지시를 확인합니다.
3. 코드 개발은 본인의 개인 feature 브랜치에서 진행하며, 사용자가 허용한 작업 범위를 준수합니다.
4. 기존 코드를 임의로 삭제하거나 대규모로 변경하지 않습니다.
5. 다른 팀원의 작업에 영향을 줄 수 있는 변경은 사전에 알립니다.
6. 수정 후 변경 파일, 주요 내용, 이유, 영향 및 추가 확인 사항을 보고합니다.
7. 테스트 실행 여부와 결과를 정확히 보고합니다.
